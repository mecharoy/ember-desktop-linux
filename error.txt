Problem: The installed desktop app got "Ollama answered with an error (403)"; the dev build never did.
Location: src/ai/providers/ollama.ts (webview fetch to Ollama)
Action: The user trying the installed 1.1.0 build with local Ollama, 2026-09-15.
Cause: The installed app's pages come from http://tauri.localhost, and tauri-plugin-http sends that as the Origin. Ollama only accepts origins on its own list (localhost with any port, 127.0.0.1, tauri://...), so it refused. The dev build's origin is http://localhost:1420, which is on the list, so every test before passed. Checked with curl: no Origin 200, Origin http://tauri.localhost 403.
Fix: Chat requests to Ollama go through Rust (local_model.rs local_chat / local_chat_cancel, streamed over a Channel), which sends no Origin. Shared helper linesFromEvents in ollama.ts is used by it and by the phone's pc.ts. Verified in the installed build: Test connection said "Connected." from http://tauri.localhost. Lesson: test the installed build, not only tauri dev, for anything network-facing.

Problem: A first version of "resets travel to the paired device" would have erased a computer's whole journal when paired with a phone reset long before.
Location: src/db/sync.ts (applyRemoteReset, applyChanges resetAt filter)
Action: Adding reset sync at the user's request, 2026-09-15.
Cause: A reset time was compared only with the receiver's own reset time, not with when the two devices last synced. The same gap made a reset phone drop the older entries of a computer paired afterwards.
Fix: A reset only applies, and older changes are only dropped, when the two last synced before that reset (staleBefore). Test "doesn't let an old reset erase, or hold back, a journal paired later".

Problem: After restoring a backup on the phone, every sync reset the phone again and erased the restored journal.
Location: src/db/sync.ts (applyRemoteReset), src/backup.ts
Action: The user restored a phone backup after a reset had already gone through both devices, 2026-09-15.
Cause: The backup carried the old sync records: "last synced with the computer" from before the reset. The computer's reset looked newer than that, so the phone applied it again, and did so after each restore.
Fix: Restore sets a flag outside the database; the next sync first calls markJournalRestored (forget peers, clear change origins), so no old reset applies and both journals merge in full. A device with no record of the other answers "fresh", and the other resends everything. Reproduced first with two failing tests (restore on phone, restore on PC); both pass now.
