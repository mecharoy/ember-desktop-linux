Problem: Every single space in src/components/Onboarding.tsx was replaced by an asterisk, in BOTH apps at once. 5928 asterisks, zero spaces, the file unparseable.
Location: elytra-desktop and elytra-mobile, src/components/Onboarding.tsx
Action: A scripted edit to export the IntroFilm component, 2026-09-22.
Cause: PowerShell array flattening, in a shape that had worked a dozen times that day. The script held its find/replace pairs as `$subs = @( @($old,$new) )` and looped `foreach ($s in $subs) { $t = $t.Replace($s[0], $s[1]) }`. With TWO OR MORE pairs, `@( @(a,b), @(c,d) )` keeps the nesting and `$s[0]` is the find string — which is why every earlier edit was correct. With exactly ONE pair, `@( @(a,b) )` FLATTENS to a two-element array of strings, `$s` becomes a string, and `$s[0]` is its first CHARACTER. The docstring being replaced began with a space and then an asterisk, so the loop ran `Replace(" ", "*")` across the whole file. `$t.Contains($s[0])` was of course true, so the script cheerfully reported "1 of 1".
Fix: Recovered the file rather than rewriting it. The corruption was a pure byte mapping (0x20 -> 0x2A), so it is reversible given one fact: the only real asterisks in a .tsx file are comment syntax — `/*`, `*/`, `//` and the decorative `*` starting a JSDoc line. scratchpad/unspace.mjs walks the text with that rule, and then PROVES the result by re-applying the corruption to it and requiring a byte-for-byte match with the damaged file. Both files matched exactly; tsc and eslint then passed on both.
Lesson: Two lessons. First, never write `@( @(a,b) )` in PowerShell — a single nested pair flattens and silently changes what the loop iterates over. Use `,@(a,b)` or two plain variables. Second, and more useful: a deterministic corruption is recoverable, and the corrupted file is its own checksum. Before rewriting a damaged file from memory or from an older copy, ask whether the damage is a reversible mapping — reversing it and proving the round trip loses nothing, where a rewrite silently drops whatever you had forgotten was in there.

Problem: Restoring a backup failed with "Expected the backup file's bytes." Reported as Elytra refusing to take an Ember backup.
Location: src-tauri/src/lib.rs, the backup_stage command (both apps)
Action: Restoring a journal from a backup file, 2026-09-22.
Cause: Nothing to do with the backup, the file, or the rename — the bytes never arrived in the form the command demanded. `backup_stage` accepted only `InvokeBody::Raw`, and Tauri only sends a raw request body over its custom-protocol IPC. On Android it NEVER does (the platform cannot read a request body, so Tauri always uses the postMessage interface), and on desktop it drops to that same fallback permanently after any single failure of the custom protocol. Over postMessage a Uint8Array is JSON-encoded as a list of numbers, so the command saw `InvokeBody::Json` and refused. Restoring on Android could therefore never have worked at all. This was inherited from Ember, unchanged; it only surfaced now because this was the first restore.
Fix: `picked_bytes()` accepts either body — raw bytes, or a JSON array of numbers it converts back. Applied to both apps. `cargo check` clean.
Lesson: A Tauri command that takes binary data must not assume the transport. `InvokeBody::Raw` is an optimisation, not a guarantee, and on Android it is never available. Accept both shapes, or send base64 and be explicit about it.

Problem: A journal entry on the PC never reached the phone, although the two were paired and syncing. Three entries were stuck this way.
Location: src/db/sync.ts, the origin filter in collectChanges
Action: Reported as "sync doesn't sync the journals", 2026-09-22.
Cause: Found by reading the real journal (a copy, structure only). The 2026-09-19 entry had a clean change-log row — rev 2222, not deleted — but `origin = 56adc928…`, the phone's own id. `collectChanges` excludes anything tagged with the peer's id, so the PC would never offer it: as far as the log was concerned the phone wrote it and therefore has it. The phone had since been reinstalled and had nothing. 122 of 581 logged changes carried that tag, 3 of them entries. The rows existed on one device, were wanted on the other, and were invisible to the sync forever.
  The tag is not wrong in itself — it stops a change bouncing straight back to its author, and it is part of how a reset travels. It is the PERMANENCE that is wrong: "you wrote it" only means "you still have it" while that device keeps its journal.
Fix: `forgetPeerOrigin(peerId)` clears a peer's tags the moment we learn it holds nothing of ours: in `answerSyncRequest` when a KNOWN peer asks with `since = 0`, and in `finishSyncRound` on the existing `fresh` path. A device that was reinstalled, cleared or restored has no peer record or a reset one, so it asks from 0 — which is exactly the case that needs the rows back. Regression test reproduces the whole story: phone writes a day, it reaches the PC, the phone is wiped, and the next round brings the day back.
  I first tried removing the origin filter altogether, on the grounds that an echo is harmless. Two tests said otherwise — a wrapped day came back skipped, and a reset stopped erasing what it should. The filter carries reset semantics as well as bandwidth, so the narrow fix is the right one.
Lesson: Two things. Any "they already have it" optimisation needs an expiry, because the other device can always lose its copy; permanent suppression turns an optimisation into data loss. And when a sync bug is reported, read the change log rather than the code — one query over a copy of the real database named the exact row, the exact tag and the exact count in a couple of minutes, where reading sync.ts had produced three plausible theories and no answer.

Problem: In the Journal, opening a day and pressing "← Journal" sometimes dropped you on the Today tab instead of the Journal list.
Location: src/useBackButton.ts (both apps); callers App.tsx and windows/Journal.tsx
Action: Reported by the user, 2026-09-23. Reproduced in a test copy: open a day, switch to Today, come back to Journal, press "← Journal".
